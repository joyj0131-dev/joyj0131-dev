# Project 04 — Under-Guard

> TurtleBot4 2대가 실내를 교대 순찰하고, 쥐 감지 시 추적·몰이 역할을 나누어 대응하는 ROS 2 기반 자율 방역 감시 시스템

- 코드 저장소: [2026_ROKEY_4_UnderGuard](https://github.com/joyj0131-dev/2026_ROKEY_4_UnderGuard)

| 항목 | 내용 |
|---|---|
| 기간 | 2026.08.05 ~ 2026.08.11 |
| 구성 | 8인 팀 프로젝트 |
| 환경 | Ubuntu 22.04, ROS 2 Humble, Python 3.10 |
| 장비 | TurtleBot4 2대, OAK-D, RPLIDAR A1 |
| 담당 | Project Manager, MySQL Database |

## 프로젝트 소개

Under-Guard는 두 대의 TurtleBot4가 실내 침입구와 덫을 순찰·점검하고, 쥐가 감지되면 각 로봇에 추적과 몰이 역할을 동적으로 배정하는 시스템입니다. SLAM·Nav2 기반 자율주행, YOLO·OAK-D 기반 객체 탐지, MySQL 기반 이력 관리와 중앙 관제를 하나의 ROS 2 시스템으로 연결했습니다.

```text
관제 화면에서 시스템 시작
→ 대기 로봇에 순찰 임무 배정
→ Waypoint 기반 침입구·덫 순찰
→ YOLO·OAK-D로 객체 탐지 및 map 좌표 변환
→ 침입구 확인 또는 기존 덫 점검
→ 쥐 감지 시 TRACK·HERD 역할 동적 배정
→ 탐지·임무·점검 결과를 MySQL에 저장
→ 배터리와 임무 상태에 따라 복귀·도킹 및 순찰 교대
```

## 시스템 구성

| 구성 요소 | 역할 |
|---|---|
| `central_node` | 시스템 시작·정지, 순찰 교대, 쥐 대응 역할 배정 |
| `robot_agent` | 로봇별 Nav2 Goal 관리, 순찰·접근·복귀·도킹 |
| `detector_node` | RGB·Depth 동기화, 객체 검출, 지도 좌표 변환 |
| `trap_check_node` | 덫 설치 지점 이동 및 정상·이상 상태 판정 |
| `herding_controller` | 표적 위치 추정과 추적·몰이 목표점 계산 |
| `db_node` | MySQL 저장 및 침입구·임무 기록 조회 인터페이스 제공 |
| System Monitor | 로봇 상태, 지도·경로와 과거 기록 시각화 |

## 담당 역할

### Project Management

- 전체 일정과 개발 계획 수립 및 진행 상황 관리
- 요구사항을 기능 단위로 정리하고 담당 모듈과 통합 순서 조율
- 모듈별 입출력 인터페이스와 기능 검증 일정 관리
- 네트워크 제약 상황에서 개별 기능·부분 연동 중심으로 시험 범위 재구성

### MySQL Database

- 침입구, 탐지, 임무와 덫 점검 이력을 위한 MySQL 데이터 구조 구성
- 중앙 PC의 `db_node`로 Database 접근 경로 단일화
- 응답이 필요한 조회는 ROS 2 Service, 비동기 저장은 Topic으로 분리
- 로봇 노드·관제 UI와 Database 간 연동 및 실행 환경 점검
- 실시간 상태 전달과 과거 기록 조회 경로를 분리해 장애 영향 범위 축소

## 핵심 설계 — Database 접근 경로 중앙화

각 로봇 노드와 관제 UI가 MySQL에 직접 연결하면 접속 정보와 스키마 의존성이 여러 모듈에 퍼지고, 변경 시 수정 범위도 커집니다. 이를 줄이기 위해 모든 Database 접근을 중앙 PC의 `db_node`로 모았습니다.

```text
Robot Nodes ── 저장 Topic ──▶ db_node ──▶ MySQL
Robot Nodes ── 조회 Service ─▶ db_node ──▶ MySQL
System Monitor ─ 조회 Service ▶ db_node ──▶ MySQL
System Monitor ◀ 실시간 Topic ─ central_node·Robot Nodes
```

탐지·상태 기록처럼 응답을 기다릴 필요가 없는 데이터는 Topic으로 전달하고, 기존 침입구 확인처럼 결과가 다음 판단에 필요한 요청은 Service로 처리했습니다. 또한 `/fleet/status`, `/fleet/event` 기반 실시간 정보와 `/db/query` 기반 과거 기록 조회를 분리해, DB 조회 문제가 실시간 로봇 상태 표시까지 중단시키지 않도록 구성했습니다.

## 문제 해결 — 제한된 네트워크 환경에서의 검증 전략

교육장 공용 네트워크에서 지연과 Ping 불안정이 반복되어 두 로봇과 중앙 PC를 연결한 전체 시나리오를 충분히 반복하기 어려웠습니다. 기능 결함과 통신 환경 문제를 구분할 수 있도록 검증 단위를 다음과 같이 나눴습니다.

- ROS·DB 없이 실행할 수 있는 로직 self-check
- DB 조회 Service와 저장 Topic 개별 확인
- 탐지·자율주행·관제 기능별 단독 시험
- Mock·Replay 기반 관제 화면과 데이터 계약 확인
- 로봇별 기능 및 가능한 범위의 부분 연동 검증

이를 통해 구현 여부와 통합 환경의 제약을 분리해 기록하고, 재시험 시 확인해야 할 항목을 명확히 남겼습니다.

## 협업을 통해 배운 점

다중 로봇 프로젝트에서는 각 기능을 개별적으로 완성하는 것만큼 모듈의 입력·출력과 통합 순서를 먼저 합의하는 일이 중요했습니다. Database 역시 단순히 저장 공간을 만드는 데서 끝나지 않고, 어떤 노드가 어떤 시점에 데이터를 기록하며 어떤 요청이 응답을 기다려야 하는지 구분해야 전체 시스템이 안정적으로 연결된다는 점을 배웠습니다.

SLAM·Nav2, AI Vision, 로봇 제어, 협동 몰이 알고리즘과 관제 UI는 각 담당자가 협업해 구현한 팀 성과입니다. 본인의 직접 담당 범위는 프로젝트 일정·개발 계획 관리와 MySQL 기반 데이터 관리 구조입니다.
